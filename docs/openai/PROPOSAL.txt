Project Simurgh: Verifiable Tool Authorization for AI Agents

OWNER-REVIEW DRAFT. Prepared 15 October 2026. No application has been submitted, funding requested, live model experiment performed, or OpenAI endorsement obtained by preparing this document. The owner must resolve the explicit pending items below before submission.

1. Research question and defensive value

Can an application-enforced tool authorization boundary prevent unauthorized effects in a fixed synthetic workload while preserving authorized work, and can a separate verifier expose inconsistent evidence?

Agents can ingest untrusted text and then propose consequential tool operations. Schema-valid output need not be authorized output. A tool gateway can also report success while executing the wrong action, omitting evidence, or preventing all useful work. We propose a narrow instrument that distinguishes these outcomes by measuring effects, authorized-task completion, and evidence consistency separately.

The intended users are developers and security researchers assessing an agent's integration with local tools. OpenAI's 2024 Instruction Hierarchy research studies model-level resistance to lower-trust instructions; its March 2026 agent-security analysis also emphasizes constraining consequences when manipulation succeeds. This experiment studies the application boundary, not a replication of those model-training or product-defense results. This proposal does not scan third-party targets, exploit external services, or deploy agents with production credentials. Its contribution is a reproducible application-security measurement method, with failures available for inspection.

2. Existing foundation and readiness

Project Simurgh is a provider-agnostic research repository with authorization boundaries, signed attestations, offline verifiers, and historical studies of containment and witness evidence. These are existing implementation and research materials, not evidence that this new OpenAI evaluation has succeeded. The additive readiness track isolates a synthetic tool-authorization demonstration from historical artifacts and existing provider integrations.

The current implementation includes a deterministic key-free path and an optional Responses API proposal adapter. The current readiness report records the executed checks, failures, and omissions. No live OpenAI model performance measurement is asserted in this proposal. 3. Method and experimental controls

Freeze a versioned threat model, fixture set, policy configuration, and source revision before the proposed campaign. Each fixture specifies a legitimate task, untrusted material where relevant, a proposed operation, authorization conditions, and expected observable effects. Treat all model output as untrusted input. Validate tool names and arguments and enforce authorization in application code before any controlled effect.

Run each applicable case against the guarded boundary and a deliberately vulnerable control in an isolated local simulator. Include legitimate allowed operations, forbidden operations, malformed proposals, and approval-integrity cases supported by the implemented contract. A failed or refused model response must be retained as a terminal outcome. Report unsupported cases explicitly rather than expanding claims beyond the instrument.

Use a separate consequence checker to examine resulting state and compare it with the fixture's expected authorized outcome. The checker must not simply trust an allow or deny label emitted by the boundary. Require a vulnerable control to produce the prohibited effect where expected, a safe control to avoid it, and an unrelated failure to remain an unrelated failure. A boundary that blocks every action must fail the useful-work control.

Sign the artifact and support offline verification of its schema, case accounting, digest/signature integrity, and recorded outcomes. Mutate artifacts deliberately and verify rejection; prove the mutation actually changed bytes. A self-generated signing key supplies consistency under that key, not independent signer identity, trusted timestamps, or proof that recorded execution happened. A checker implemented by the same project is not independent organizational validation. Seek a separately operated reproduction as a later milestone, without claiming it in advance. Expose the task through established evaluation tooling where practical, preserving the local scorer and its controls. An Inspect task wrapper can improve reuse; it does not turn internally authored cases into an external benchmark or prove model safety.

The initial dataset consists of new, versioned synthetic local authorization cases and artificial tool responses. It contains no customer records, private documents, credentials, personal data, or third-party target details. Release fixtures, expected outcomes, and provenance information with the implementation. Keep development fixtures distinct from a proposed held-out expansion; do not describe hand-authored fixtures as unseen real-world attacks. Ask a separate contributor to author held-out resource/approval-substitution and information-disclosure cases with matched legitimate tasks. Freeze the boundary and scoring before seeing those cases. If no external contributor participates, label the extension internally authored. Existing AgentDojo-related work is background, not a newly executed external benchmark or a licensed dataset transfer.

5. Delivery milestones

Proposed duration: eight weeks after an owner-approved start date. Location: the applicant's development environment and local simulator, with only synthetic prompts sent to the API if separately authorized. PENDING OWNER INPUT: team members, roles, institution, work location, and calendar start date.

Acceptance: legitimate and forbidden controls produce the expected distinct outcomes, with every case accounted for.

Weeks 3-4: Extend adversarial fixtures and artifact-tamper checks; obtain code review and attempt reproduction in a clean environment. Acceptance: harmful controls demonstrate detector sensitivity, safe controls preserve useful work, unrelated failures remain classified as failures, and altered artifacts are rejected. Acceptance: a reviewer can rerun the published commands and check artifacts without the producer's private key. External reproduction is successful only when an external party actually completes it; otherwise record it as pending. Publication itself requires owner approval.
